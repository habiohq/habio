# v0.1 scope and acceptance

## Goal

Habio v0.1 proves that a small, local execution boundary can report what is
known about a physical action without confusing transport success, provider
acceptance, observation, and verification.

It is not a complete Physical AI platform. Its first vertical is an experiment
used to validate reusable execution semantics.

## Core ownership

The core owns only concepts that must retain the same meaning across providers:

- immutable Action intent and identity;
- distinct ExecutionAttempt identity;
- dispatch and receipt evidence;
- outcome knowledge, including explicit unknowns;
- timestamped observations;
- verification results and their supporting evidence;
- append-only execution facts and reconstructable projections; and
- replay-safety information without automatic recovery policy.

The core also supplies enforcement and extension points, but not the concrete
policy or integration installed at those points.

## Edge and application ownership

| Concern | Owner | Reason |
| --- | --- | --- |
| MCP/API request shape | Adapter | Call protocol can change independently. |
| Device discovery and registry | Provider/platform | The hardware platform already owns it. |
| Home Assistant entities and services | Home Assistant provider | They are integration details, not universal semantics. |
| MHS variables, controls, and drivers | MHS provider | Habio must not duplicate MHS. |
| Matter, MQTT, Zigbee, Modbus, OCPP | Provider | Protocols live at the edge. |
| Authorization and domain safety rules | Admitter extension/application | Core owns the enforcement point, not policy. |
| Natural-language interpretation and planning | Caller/strategy authoring | Action input to core is already structured. |
| Workflow and automation logic | Strategy/application | Execution does not decide what should happen. |
| Managed history, fleets, billing, RBAC | Cloud product | Local execution must remain independent. |

## Explicit non-goals for v0.1

- canonical Light, AC, TV, EV, HVAC, or robotics types;
- a universal capability taxonomy;
- device discovery or vendor drivers;
- a dynamic plugin manager or provider registry;
- an out-of-process provider protocol;
- automatic retry of ambiguous actions;
- a full event-sourcing platform or durable cloud sync;
- a Strategy runtime, conflict engine, or marketplace;
- a SaaS control plane, remote connectivity, or billing; and
- a production-ready Home Assistant integration.

## Acceptance matrix

| Capability | Executable evidence | Required result |
| --- | --- | --- |
| Action and attempt identity | Execute one Action, then explicitly create a second attempt for it. | One Action ID, two unique Attempt IDs, unchanged intent. |
| Known pre-dispatch rejection | An Admitter rejects a fixture Action. | No Provider call; rejection evidence is retained. |
| Provider acknowledgement | Fake Provider returns an acceptance receipt. | Result says acknowledged, not verified. |
| Ambiguous timeout | Fake Provider may dispatch, then returns a timeout with no conclusive receipt. | Outcome remains unknown; no automatic retry. |
| Unsafe replay visibility | Mark or assess a `toggle`-like fixture as not safely replayable. | Caller can see that recovery requires an explicit decision. |
| Independent observation | Provider dispatches and another Observer reports desired state. | Verification can succeed despite the separate evidence path. |
| Missing observation | Provider acknowledges but Observer cannot supply evidence. | Result remains unverified, not successful by implication. |
| Stale observation | Observer returns desired state older than the allowed freshness. | Verifier does not accept it as sufficient evidence. |
| Contradictory observation | Fresh evidence reports an undesired state. | Verification reports unsatisfied with evidence. |
| Reconstructable status | Replay recorded facts into an in-memory projection. | Projected view matches the final known evidence. |
| Home Assistant vertical | Exercise light, climate, and media-player fixtures locally. | Verified, unverified, and unknown cases are demonstrated without device types in core. |
| Honest adapter output | Render each result through a minimal adapter response. | Unknown/unverified never becomes a claim of physical success. |
| Third-party extension | Implement the minimum contracts in a package that imports core. | No adapter, Home Assistant, MCP, or cloud dependency is needed. |
| Local-only execution | Run the proof with all Habio cloud endpoints absent. | Dispatch, observation, verification, and local facts still work. |

## Boundary review checks

A proposed core change fails scope review if any answer below is yes without an
accepted RFC:

1. Does it introduce a device, vendor, protocol, MCP, or Home Assistant concept?
2. Does it choose authorization, safety, retry, or business policy for callers?
3. Does it turn missing evidence into success or failure?
4. Does it make local execution depend on a Habio cloud service?
5. Can this concept evolve on an independent release cycle?
6. Is the abstraction derived only from the first provider implementation?
7. Does it add infrastructure before an acceptance case requires it?

## Completion

v0.1 is complete when every row in the acceptance matrix is backed by a test or
reproducible local trace and the dependency rules in `ARCHITECTURE.md` remain
true. Marketplace, SaaS, and broad device coverage are not release criteria.
